# Совместная озвучка

Дата: 2026-09-01

## Задача

Дать нескольким людям озвучить один пак вместе, каждому со своего компьютера. Сегодня «Дубль» — игра на одного: `Record` ведёт человека по всем репликам подряд, тейки складываются в папку пака, `Results` показывает оценки, `Watch` сводит дорожку и отдаёт её на экспорт.

## Что решено

- Участники сидят за разными компьютерами и играют одновременно.
- Проход общий и последовательный: после каждой реплики сессия ждёт, автор решает — перезаписать или идти дальше.
- Голосовой чат остаётся снаружи (Discord, одна комната). Игра не передаёт живой звук.
- Соединение — P2P через WebRTC, с TURN-фолбэком, когда прямое не встаёт.
- Рукопожатие — через собственный WebSocket-сервис: хост получает код комнаты, остальные его вводят.
- Каждый тейк разлетается всем участникам. После сессии у каждого свой полный дубляж: свои итоги, свой просмотр, свой экспорт.
- Роли разбираются в лобби самими участниками. Старт доступен, только когда разобраны все персонажи пака.
- Совместная сессия сохраняется отдельным дублем и не затирает соло-проход.
- Проход по репликам двигает только их автор: за другого не ходит даже хост. Хост, оставшийся без пропавшего участника, сначала забирает его роли себе.
- Позиция прохода общая, но смотреть и слушать любой может любую реплику, не сбивая её.
- Обрыв связи ставит сессию на паузу; вернувшийся по тому же коду догоняет состояние.
- Итоги показывают автора у каждой реплики и сводку по участникам.

## Что не входит

Голосовой и текстовый чат внутри игры. Синхронный «живой прогон» без пауз. Зрители без ролей. Публичный список комнат, аккаунты, рейтинги между сессиями. Передача самого пака между участниками — пак каждый ставит с витрины сам.

## Модель данных

Пак сейчас хранит ровно один проход прямо в своей папке. Вводится понятие дубля:

```
packs/<slug>/
  pack.json  video.mp4  backing.wav  icon  cover      — пак, общий для всех дублей
  dubs/<dubId>/
    dub.json                 — описание дубля
    takes.json               — TakesMap
    takes/<lineId>.wav
    mix.wav
```

`dubId` — `solo` для одиночного прохода и `coop-<timestamp>-<rand>` для совместных.

```ts
interface DubInfo {
  id: string;
  kind: "solo" | "coop";
  createdAt: number;
  updatedAt: number;
  participants: DubParticipant[];   // для solo — пустой
  roles: Record<string, string>;    // имя персонажа -> id участника
}

interface DubParticipant {
  id: string;
  name: string;
}
```

У тейка появляется автор:

```ts
interface TakeInfo {
  // как сейчас: file, duration, recordedAt, takeCount, analysis
  authorId?: string;   // отсутствует у соло-тейков
}
```

Перевод остаётся на уровне пака: он общий для всех дублей и лежит там же, где сейчас.

### Миграция

При первом чтении пака новой версией существующие `takes.json`, `takes/` и `mix.wav` переносятся в `dubs/solo/`. Приём тот же, что уже применён для `translation-ru.json`: читаем новое место, при промахе читаем старое и переписываем в новое. Пак без тейков получает пустой `dubs/solo/` при первой записи.

### Rust

- `export_video(slug, dubId, title)` — берёт `dubs/<dubId>/mix.wav` вместо `mix.wav`.
- `list_dubs(slug) -> Vec<String>` — имена подпапок `dubs/`, где лежит `dub.json`.
- `delete_dub(slug, dubId)` — удаляет папку дубля.

Остальные файловые команды уже принимают произвольный `rel` и проверяют его через `safe_rel`, новых не нужно.

## Архитектура клиента

`Record.tsx` сегодня держит три вещи разом: машину записи одной реплики, навигацию по списку реплик и вёрстку. Разделяем:

- `audio/takeEngine.ts` — машина одной реплики: `orig → idle → lead → rec → done → take`, разбег, обрезка по окну фразы, анализ. Не знает ни про список реплик, ни про сеть.
- `session/state.ts` — состояние прохода и чистый редьюсер: текущая реплика, чей ход, фаза сессии, участники, роли, права на команды.
- `session/local.ts` — драйвер соло: команды приходят от кнопок, применяются сразу.
- `session/network.ts` — драйвер совместной сессии: свои команды уходят хосту, чужие приходят от него и применяются тем же редьюсером.
- `screens/Record.tsx` — вёрстка поверх состояния, одна для обоих режимов.
- `screens/Lobby.tsx` — создание комнаты, вход по коду, разбор персонажей, готовность к старту.
- `dubs.ts` — чтение и запись дублей, миграция, список дублей пака.

`Results` и `Watch` начинают работать с парой `(slug, dubId)`.

## Сеть

Топология — звезда. Хост держит по одному `RTCPeerConnection` с каждым гостем и остаётся единственным источником истины о состоянии прохода. Гости говорят только с хостом. Мешевые соединения не нужны: трафик копеечный, а один авторитет снимает вопрос согласования состояний.

- `net/signaling.ts` — WebSocket-клиент рукопожатия.
- `net/peer.ts` — обёртка над `RTCPeerConnection` и надёжным упорядоченным DataChannel. Бинарные тейки едут чанками по 16 КБ: сначала JSON-заголовок с `lineId`, `authorId` и размером, следом чанки, на приёме — сборка.
- `net/protocol.ts` — типы сообщений.

### Сигналинг

Отдельный Node-сервис в папке `server/` этого репозитория. Комнаты живут в памяти, TTL — час без активности. Код комнаты — шесть символов из алфавита без похожих начертаний.

Клиент → сервер: `create-room`, `join-room {code}`, `signal {to, payload}`, `leave`.
Сервер → клиент: `room-created {code, peerId}`, `room-joined {peerId, hostId}`, `peer-joined {peerId}`, `peer-left {peerId}`, `signal {from, payload}`, `error {reason}`.

После установки DataChannel сервис в сессии не участвует. Он же не хранит ни тейков, ни состояния — только список подключённых сокетов комнаты.

### TURN

`RTCPeerConnection` получает список STUN и TURN-серверов из конфигурации приложения. Когда ICE не собрал прямой путь, соединение уходит через TURN. Если и это не вышло, лобби честно показывает, что соединиться не удалось, и предлагает попробовать снова.

## Протокол сессии

Все сообщения гостя идут хосту, хост применяет их к состоянию и разлетает результат всем. Гость применяет только то, что пришло от хоста.

| Сообщение | От кого | Смысл |
|---|---|---|
| `hello {participantId, name, packSlug, linesHash}` | гость | представиться и заявить свой пак; шлётся повторно, когда пак нашёлся |
| `lobby-state {participants, roles, packSlug, canStart}` | хост | полное состояние лобби |
| `claim-character {character}` / `release-character {character}` | любой | взять или отдать персонажа |
| `start {order}` | хост | начать проход |
| `line-begin {lineIndex}` | хост | все отматывают видео на разбег, автор пишет |
| `take {lineId, authorId, takeCount, analysis, duration}` + чанки WAV | автор → хост → все | готовый тейк |
| `retake {lineId}` | автор | переписать текущую реплику |
| `advance {nextIndex}` | автор | идти дальше |
| `goto {lineIndex}` | автор текущей или целевой реплики | перевести проход на реплику, чтобы переписать её |
| `pause {reason}` / `resume` | хост | пауза при обрыве и снятие паузы |
| `reassign {character, toParticipantId}` | хост | передать роль другому участнику |
| `snapshot {sessionState, takenLineIds}` | хост | состояние для вернувшегося |
| `request-takes {lineIds}` | гость | догрузить тейки, которых у него нет |
| `finish` | хост | проход закончен |

`linesHash` считается по идентификаторам реплик и их границам. Несовпадение означает, что у гостя другой пак или другая его версия: он попадает в лобби со статусом «пак не подходит», старт заблокирован.

## Ход сессии

Фазы: `lobby → running → paused → finished`.

**Лобби.** Хост выбирает пак из библиотеки и создаёт комнату — получает код. Гость вводит код, ещё не зная пака: состояние сессии называет ему `packSlug`, и клиент сам находит пак в библиотеке и представляется заново. Если пака нет, гость видит предложение поставить его с витрины; пока пак не готов, старт заблокирован. Персонажей разбирают сами, один участник может взять несколько. Кнопка «Начать» доступна хосту, когда каждый персонаж кем-то взят и все подключены.

**Реплика.** Хост шлёт `line-begin`. У всех локальное видео отматывается на разбег текущей реплики и играет. Пишет только владелец персонажа: у него запускается `takeEngine`, остальные видят «пишет Аня» и оригинальную дорожку. По окончании автор шлёт тейк, хост разлетает его всем, у каждого он ложится в свой дубль и сразу проигрывается со сценой — слушают вместе. Дальше автор жмёт «ещё дубль» или «дальше». Остальные в это время могут листать реплики у себя — слушать чужие дубли и оригинал, — а вернуться к проходу помогает кнопка «Вернуться к прогону»; записывать вне прохода нельзя.

**Реплики без записи.** Их нет: старт возможен только при полностью разобранных персонажах.

**Обрыв.** Хост видит закрытие канала и переводит сессию в `paused` — у всех висит «ждём Аню». Вернувшийся вводит тот же код, получает состояние и запрашивает недостающие тейки. Хост может вместо ожидания забрать роли пропавшего себе или продолжить проход без него: его реплики останутся оригинальными.

**Отвал хоста.** Гости остаются с тем, что уже записано: дубль лежит локально целиком, его можно свести, посмотреть и экспортировать. Продолжить сессию нельзя — нужен новый проход.

**Финиш.** Хост шлёт `finish`, каждый клиент дописывает `dub.json` и открывает итоги своей копии дубля.

## Итоги и экспорт

`Results` получает `dubId`. У каждой реплики виден автор — имя участника рядом с именем персонажа. Сверху сводка: участник, число реплик, среднее попадание в тайминг. Сравнение построено на том же `analysis`, что считается сейчас. `Watch` сводит `dubs/<dubId>/mix.wav` и экспортирует видео из своей копии.

Библиотека показывает у пака список дублей: соло-проход и совместные с датой и составом. Запись, итоги и просмотр открываются для выбранного дубля, дубль можно удалить.

## Тестирование

Юнит-тестами: редьюсер сессии (права автора и хоста, запрет старта с неразобранными ролями, пауза и возврат, порядок реплик), сборка и разборка чанков бинарного сообщения, миграция пака на дубли, сводка по участникам в итогах.

Интеграционным тестом: полный проход — лобби, две реплики, ретейк, обрыв, возврат со снапшотом и догрузкой тейков, финиш — на двух экземплярах сессии, соединённых транспортом в памяти. Тест проверяет протокол и состояния, не трогая WebRTC.

Сигналинг-сервис — интеграционным тестом через настоящий WebSocket: комната, код, разлёт SDP, отключение.

Живое P2P между двумя машинами проверяется руками: оно зависит от сети и не автоматизируется.

## Этапы

1. **Дубли в хранилище.** Модель дубля, миграция, `list_dubs`, `delete_dub`, `export_video` с `dubId`, библиотека со списком дублей, `Results` и `Watch` на паре `(slug, dubId)`. Ценность сама по себе: несколько проходов одного пака.
2. **Движок и драйвер.** Выделение `takeEngine`, состояние сессии с редьюсером, локальный драйвер, `Record` поверх состояния. Соло работает как раньше, но уже через новую машину.
3. **Сеть и совместный режим.** Сигналинг-сервис, WebRTC-транспорт, протокол, лобби, совместный проход, авторы и сводка в итогах.
